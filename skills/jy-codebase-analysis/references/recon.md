# Survey (Recon) and Work-Unit Planning

Phase 1 is a **shallow** pass by the orchestrator. Read structure and
signposts, not function bodies. Its job is to map the whole system well enough
to split it into work units and give each worker useful context. It is not
meant to understand the logic.

Use whatever file tools your agent has. Prefer `git ls-files` for the
inventory because it honors `.gitignore`. Use `wc -l` (or an equivalent) for
line counts.

## 1. Inventory

1. List every tracked file with its line count. Record the totals: file count,
   line count, and the breakdown by extension.
2. Apply the **skip rules** (below). Write each skipped file, or a glob
   covering a homogeneous group, to `skipped.md` with its reason.
3. Everything that is left is **in scope**, and every in-scope file must land
   in exactly one work unit.

### Skip rules

| Skip | How to recognize it | Reason to log |
|---|---|---|
| Generated code | Header like `DO NOT EDIT`, `@generated`, `autogenerated`; `*_pb2.py`, `*.g.cs`, `*.generated.*`, OpenAPI/GraphQL client output dirs | generated — note the source spec (`.proto`, `.graphql`, OpenAPI file); **the source spec is in scope** |
| Vendored / third-party | `vendor/`, `third_party/`, `node_modules/`, copied libraries with foreign license headers | vendored |
| Lockfiles | `package-lock.json`, `yarn.lock`, `poetry.lock`, `Cargo.lock`, `go.sum`, … | lockfile — the manifest (`package.json`, …) is in scope |
| Minified / bundled | `*.min.js`, `dist/`, `build/`, single-line files over ~1000 chars | build output |
| Binary and media | images, fonts, archives, compiled artifacts | binary |
| Large data fixtures | CSV/JSON/SQL dumps over ~500 lines that are data, not schema | data — sample the header and first rows in the owning unit's context, and note that it exists |

When in doubt, keep the file in scope as `light`. A skipped file that held
business logic is a coverage failure, and an extra light read is cheap.

**Never skip**: SQL schemas, migrations, stored procedures, rule or config
files (YAML/JSON/TOML that drive behavior), spreadsheet-like rate tables,
feature-flag definitions, validation schemas, or `.proto`/OpenAPI source
specs. Business rules often live in these files.

## 2. Signposts to read

Read these in roughly this order, and stop each read once it has given you what you need:

1. **Docs**: `README*`, `docs/`, `ARCHITECTURE*`, ADRs, `CONTRIBUTING*`,
   `CLAUDE.md`/`AGENTS.md`/`.cursor/rules`/`.github/copilot-instructions.md`
   (these often state intended conventions — treat them as claims to check,
   not facts).
2. **Build and dependency manifests**: languages, frameworks, runtime
   versions, and notable libraries (ORM, web framework, messaging, math and
   finance libraries such as `decimal`, `BigDecimal`, numpy, QuantLib).
3. **Deployment and infrastructure**: Dockerfiles, compose files, k8s/Helm,
   Terraform, CI workflows. These show which processes and containers exist
   and what they talk to.
4. **Entry points**: `main`, server bootstraps, route and controller
   registration, CLI command tables, job and cron schedulers, message
   consumers, serverless handlers.
5. **File headers**: the first ~30 lines of every in-scope source file:
   package/namespace declarations, imports, module docstrings, and class or
   function signatures. Imports are how you build the reference graph.
6. **Directory names**: layer and feature signals (`domain`, `application`,
   `infrastructure`, `adapters`, `ports`, `controllers`, `services`,
   `repositories`, `usecases`, `handlers`, `features/<x>`).

## 3. Build the system map

Write `system-map.md`:

```markdown
# System Map (provisional)

**Hypothesis:** <one paragraph — what this system appears to be, for whom, and
what it does. Mark it provisional.>

## Stack
<languages, frameworks, runtimes, persistence, messaging — with manifest citations>

## Entry points
| Entry point | Kind (HTTP / CLI / job / consumer / UI) | Path |

## Candidate components
| Component | Directories | Apparent responsibility | Layer(s) |

## Layering hypothesis
<the layering style the directory structure suggests (layered, hexagonal,
clean, feature-sliced, MVC, none evident) and the observed dependency
direction from imports>

## External integrations
| System | How (HTTP client, SDK, queue, DB, file) | Evidence |

## Seed glossary
| Term | Where seen | Tentative meaning |
```

## 4. Partition into work units

A **work unit** is a group of related files that one worker reads in full.
Good units let the worker understand a feature or layer slice end to end.

**Grouping priority:**

1. Keep a feature or component together across its files (for example a
   service, its model, and its repository in one feature folder).
2. Otherwise group by directory within a layer.
3. Put tests with the code they test when the combined unit still fits. When
   it doesn't, make a separate test unit for that component. Tests often state
   business rules more plainly than the code does.
4. Group config, rule files, and migrations with the component that consumes
   them, or put them in a dedicated "configuration and schema" unit.

**Sizing** (in source lines; adjust down for dense code such as math-heavy or
SQL-heavy files):

- Target **1,500–3,000 lines** per `deep` unit. Hard ceiling **4,000**.
- `light` units can be about 2× larger.
- A single file above the ceiling becomes its own unit. If it's still too big,
  split it into line ranges that overlap by about 50 lines, and tell each
  worker which range it owns.

**Depth tier:**

- `deep`: domain logic, services, use cases, calculations, validation, rule
  engines, SQL with logic, anything with arithmetic on business quantities,
  and controllers or handlers that contain logic. **When in doubt, deep.**
- `light`: pure wiring, DTOs with no behavior, straightforward CRUD
  boilerplate, UI markup without logic, build scripts, test fixtures and
  factories. Light still means every line is read. The card can simply be
  briefer about files that turn out to hold nothing notable.

## 5. Manifest format

Write `manifest.md`. It is the single source of truth for progress and resume.

```markdown
# Work Unit Manifest

Totals: <N> tracked files, <M> in scope, <S> skipped, <L> in-scope lines, <U> units.

| Unit | Name | Component | Layer | Tier | Files | Lines | Status |
|---|---|---|---|---|---|---|---|
| U-001 | Loan domain core | Lending | domain | deep | 6 | 1,840 | pending |

## U-001 files
- src/lending/domain/loan.py
- ...
```

Status values: `pending` → `dispatched` → `done` | `failed` → `verified`.

Before leaving Phase 1, check: (in-scope files across all units) + (skipped
files) = (tracked files). If the numbers don't reconcile, fix the plan before
dispatching.
